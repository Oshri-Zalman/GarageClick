# Software Requirements Specification (SRS) - GarageClick
## גרסה 2.1 - סופית

**תאריך:** יוני 2026  
**סטטוס:** אושרה לפיתוח  
**מעדכן:** כל החידושים מהשיחה

---

## 1. System Overview

### 1.1 System Purpose

מערכת GarageClick היא אפליקציית Web המיועדת לארגון וניהול של מוסכים בצורה פשוטה ויעילה. המערכת מחליפה את הניהול במערכות ישנות ומסובכות ומספקת פתרון טכנולוגי מודרני לניהול העבודות בזמן אמת.

המערכת מאפשרת למשתמשי המוסך:
- **ניהול רישומי לקוחות ורכבים** בצורה דיגיטלית ופשוטה
- **פתיחה וניהול כרטיסי עבודה** עם Kanban board לצפייה בזמן אמת
- **צמצום טעויות אנוש** באמצעות State Machine שמאכוף תהליכי עבודה
- **עדכוני חלפים חכמים** - בחירה מתוך מלאי קיים עם validation אוטומטי
- **שקיפות ללקוח** - הודעות WhatsApp כשרכב מוכן לאיסוף

### 1.2 System Scope

**פיצ'רים שנכללים:**
- **ניהול משתמשים בעלי 3 תפקידים:** Manager, Secretary, Mechanic (כל אחד בהרשאות שונות)
- **ניהול לקוחות והיסטוריה:** פרופילים, רכבים, חיפוש מהיר
- **Kanban Board:** 3 עמודות עם גרירה וכפתורים
- **State Machine:** transitions חוקיים בלבד (Pending → In Progress → Completed)
- **ניהול כרטיסי עבודה:** יצירה, שיוך עובדים, ניהול סטטוסים
- **ניהול מלאי חלפים:** דאטה בס עם Compatibility Matrix וValidation
- **הודעות אוטומטיות:** WhatsApp כשרכב מוכן לאיסוף
- **כלים ניהול (Manager):** ניטור עובדים, סטטוס לפי ימים, ניהול משתמשים, דוחות ביצועים
- **סטטוס סטאטיסטי (Secretary):** צפייה בכל הכרטיסים וסטטוסים

**מה לא בכלל (Future Extensions):**
- אפליקציית Mobile Native
- פורטל לקוח (רק WhatsApp)
- תשלומים וחיוב
- שפות אחרות (עברית בלבד)

## 3. Functional Requirements

### **FR-1: ניהול לקוחות ורכבים**

המערכת תאפשר ל-Manager, Secretary ו-Mechanic ליצור, לערוך ולחפש פרופילי לקוחות.

**פעולות בסיסיות:**
- יצירה, קריאה, עריכה של פרופילי לקוחות
- מזהה ייחודי אוטומטי לכל לקוח (ID_Customer)
- **חיפוש מהיר** לפי מספר רכב או מספר טלפון

**שדות בפרופיל לקוח:**
- שם מלא
- מספר טלפון (עבור WhatsApp)
- מספר רכב/לוחית רישום

---

### **FR-2: פתיחת כרטיסי עבודה (כולל קליטת לקוח)**

**מי יכול לפתוח:**
- **Manager** (תמיד, על עצמו או על עובד אחר)
- **Secretary** (תמיד, על עובד אחר)
- **Mechanic** (אופציונלי - לפי הגדרת המוסך, על עצמו בלבד)

**Flow של פתיחה:**

**סדר פתיחת כרטיס (Flow חדש):**

**שלב 1: חיפוש/הזנת מספר רכב (license_plate)**
```
טופס פתיחת כרטיס:
┌──────────────────────────────────┐
│ הזן מספר רכב:  [_____________] │
│                    [🔍 חפש]      │
└──────────────────────────────────┘

אם רכב קיים → המערכת מוצאת אותו + כל הפרטים
אם רכב לא קיים → טופס ליצירת לקוח חדש + רכב חדש
```

**אפשרות A: רכב קיים - Auto-Fill**
```
1. עובד/Secretary מזינים מספר רכב: "123-456"
2. Frontend: GET /api/vehicles/search?license_plate=123-456
3. Backend מחזיר: {vehicle_id, license_plate, manufacturer, model, year, 
                    customer_id, customer_name, customer_phone}
4. Frontend: ממלא אוטומטי:
   - שם לקוח: דן
   - טלפון לקוח: 050123456789
   - סוג רכב: Volkswagen (זוהה)
   - מודל: Golf (זוהה)
   - שנה: 2018 (זוהה)
   
5. עובד ממלא:
   - תיאור התקלה
   - בוחר חלפים (compatible לVW Golf 2018)
   
6. לחץ "פתח כרטיס"
```

**אפשרות B: רכב לא קיים - יצירת לקוח + רכב חדשים**
```
1. עובד מזין: "999-999"
2. Backend: רכב לא קיים
3. Frontend: הצג טופס ליצירה:
   
   לקוח חדש:
   - שם מלא: [________________] (required)
   - טלפון: [________________] (required)
   
   רכב חדש:
   - מספר רכב: [999-999] (נתון)
   - סוג רכב: [dropdown - VW/BMW וכו'] (required)
   - מודל: [________________] (required)
   - שנה: [________________] (required)
   
   תיאור התקלה: [________________] (required)
   בחירת חלפים: [compatible לרכב החדש] (required)
   
   [פתח כרטיס]

4. Backend:
   a. CREATE customer (שם + טלפון)
   b. CREATE vehicle (רכב חדש בשם הלקוח)
   c. CREATE ticket + deduct parts
```

**שדות כרטיס (סדר חדש):**
- **1. מספר רכב** (license_plate) - הצעד הראשון
- **2. לקוח** (auto-fill אם קיים, או יצירה אם חדש)
- **3. רכב** (auto-fill אם קיים, או יצירה אם חדש)
- **4. עובד מטפל** (auto-assign אם Mechanic פתח על עצמו, או בחירה אם Secretary/Manager)
- **5. תיאור התקלה** (required)
- **6. זמן סיום משוער** (אופציונלי)
- **7. בחירת חלפים** (required - חלפים compatible בלבד)
- **8. ID_Ticket** (אוטומטי)
- **9. חותמת זמן** (אוטומטי)
- **10. סטטוס התחלתי** (Pending)

---

### **FR-3: ניהול סטטוסים עם State Machine**

המערכת תנהל את מחזור החיים של העבודה עם enforcement של transitions חוקיים בלבד.

**3 סטטוסים:**
1. **Pending (ממתין לטיפול)** - כרטיס חדש
2. **In Progress (בטיפול)** - עובד עובד בפועל
3. **Completed (סיום טיפול)** - הטיפול הסתיים

**Transitions חוקיות:**
- **Pending → In Progress:** לחיצה על כפתור "קבל" (אין אישור נדרש)
- **In Progress → Completed:** לחיצה על כפתור "סיים טיפול" (אישור מפורש נדרש!)
- **בעת סיום:** המערכת שולחת WhatsApp ללקוח אוטומטית

**מי יכול לעדכן:**
- **Mechanic:** עדכן את הכרטיסים שלו דרך הKanban
- **Secretary:** יכולה לעדכן סטטוסים של כל הכרטיסים (עבור גמישות)
- **Manager:** יכול לעדכן סטטוסים של כל הכרטיסים (כל ההרשאות)

---

### **FR-4: Kanban Board (לוח עבודה)**

תצוגה ויזואלית של כל הכרטיסים בעיצוב Kanban עם שלוש עמודות ומעברים אוטומטיים.

**עמודות קבועות:**
- ⏳ **Pending** (ממתין לטיפול)
- ⚙️ **In Progress** (בטיפול)
- ✅ **Completed** (הטיפול הסתיים)

**מה מציג כל קלף:**
- מספר רכב (bold)
- תיאור קצר של הטיפול
- שם העובד המטפל
- סטטוס בצבע
- **כפתורים:** "קבל" ו-"סיים טיפול" (תלוי בעמודה)

**אינטראקציה (ללא Drag & Drop):**

**בעמודת Pending:**
- כפתור **"קבל"** (Pending → In Progress)
- כשלוחצים → קלף עובר אוטומטית לעמודה In Progress
- **אין אישור נוסף נדרש**

**בעמודת In Progress:**
- כפתור **"סיים טיפול"** (In Progress → Completed)
- כשלוחצים → **אישור מפורש** נדרש
- אם אישור → קלף עובר אוטומטית ל-Completed
- **בשלב זה:** המערכת שולחת WhatsApp ללקוח אוטומטית

**בעמודת Completed:**
- קלף מוצג ללא כפתורים (רק עריכה אם צריך)
- קלף שהר בארכיון

**סינור סטטוסים:**
- אפשרות לסנן לפי סטטוסים

**מדדים:**
- ספירה של כמה קלפים בכל עמודה

**צפייה לפי תפקיד:**
- **Manager:** כל הKanban (כל העובדים) - יכול לעדכן ולראות
- **Secretary:** כל הKanban (כל העובדים) - יכולה לעדכן ולראות
- **Mechanic:** רק הKanban שלו (הכרטיסים שהוקצו לו) - יכול לעדכן

---

### **FR-5: עדכוני הודעות אוטומטיות (WhatsApp)**

המערכת תשלח הודעת WhatsApp ללקוח בנקודה אחת בלבד: כשהטיפול מושלם.

**מתי בדיוק:**
- כשעובד או Secretary לוחצים על כפתור "סיים טיפול"
- **לאחר אישור מפורש** (כדי לא לשלוח בטעות)
- המערכת עדכנה סטטוס ל-"Completed"
- **מיד לאחר מכן:** משלחת WhatsApp אוטומטית

**תוכן ההודעה:**
- "הטיפול ברכבך הסתיים! ניתן להגיע לאיסוף"
- מספר כרטיס עבודה (ID_Ticket)
- אופציונלי: זמן משוער של הגעה

---

### **FR-6: כלים ניהול (Manager בלבד) + הרשאות כוללות**

**הערה חשובה:** Manager בעל **כל ההרשאות** של Secretary וMechanic בנוסף לשלו.

זה אומר Manager יכול:
- ✅ לפתוח כרטיס עבודה על עצמו (כמו Mechanic)
- ✅ לפתוח כרטיס לעובד אחר (כמו Secretary)
- ✅ לעדכן סטטוסים (כמו Mechanic/Secretary)
- ✅ לבחור חלפים (כמו Mechanic)
- ✅ לנהל מלאי (כמו Secretary)
- ✅ **בנוסף:** גישה לכל הכלים הניהול המפורטים למטה

**כלים ניהול ייחודיים למנהל בלבד:**

**6.1 סטטוס בקרה עובדים (Real-time Monitoring):**
- טבלה המציגה:
  - שם עובד
  - סטטוס (online/offline)
  - כמה כרטיסים פתוחים עכשיו
  - כמה כרטיסים הושלמו היום
  - זמן התחברות/התנתקות

**6.2 סטטוס כרטיסים (סיכום יומי):**
- סיכום כולל של היום:
  - כמה כרטיסים ב-Pending
  - כמה ב-In Progress
  - כמה ב-Completed
  - זמן טיפול ממוצע

**6.3 סטטוס לפי ימים (ניתוח עומס):**
- צפייה בביצועים לפי יום בשבוע:
  - כמה כרטיסים פתוחים בכל יום
  - כמה הושלמו בכל יום
  - זמנים ממוצעים לפי יום
  - **מגמות צריכה ועומס** (איזה ימים עמוסים יותר)

**6.4 ניהול משתמשים:**
- הוספת משתמש חדש (בחירת role: Manager/Secretary/Mechanic)
- הגדרת שם משתמש וסיסמה זמנית
- מחיקת משתמש
- החלפת סיסמה

**6.5 דוחות ביצועים (ניתוח איכות עבודה):**
- **חשוב:** לא כמויות, אלא איכות!
- סטטיסטיקות:
  - **זמן טיפול ממוצע** (כמה שעות בממוצע כל כרטיס)
  - **ביצועי כל עובד:** זמן עבודה כולל, כרטיסים הושלמו, איכות הטיפול (כרטיסים קלים vs קשים)
  - **ניתוח קושי:** עובד A טיפל ב-1 כרטיס קשה למשך 8 שעות vs עובד B טיפל ב-9 כרטיסים קלים
  - **מגמות:** טרנדים בביצועים לאורך זמן

---

### **FR-7: ניהול מלאי חלפים (Secretary בעיקר)**

המערכת תנהל דאטא בס של חלפים עם validation וUpdate אוטומטי.

**7.1 הזנת מלאי (Secretary/Manager):**
- סוג רכב (Volkswagen, BMW, וכו')
- מודל (Golf, 320i, וכו')
- טווח שנים (2015-2020)
- שם חלף (בלמים דיסק קדמי)
- מקט/SKU (part_code)
- כמות זמינה

**7.2 בחירת חלפים בעת פתיחת כרטיס:**
- **כשMechanic פותח כרטיס:**
  - המערכת מזהה רכב (סוג + מודל + שנה)
  - **מציגה רק חלפים תואמים** (Compatibility Matrix)
  - אם חלף = 0:
    - ❌ כפתור בחירה **מנוטרל** (disabled)
    - ❌ הודעה אדומה: "החלק אינו זמין במלאי"

- **כשSecretary פותחת כרטיס לעובד:**
  - גם היא יכולה לבחור חלפים (כי היא משיימת את הכרטיס לעובד)
  - אותם כללים כמו Mechanic: רק חלפים תואמים, אם אין → disabled

**7.3 אפשרות "אחר" (לכרטיסים ללא חלפים):**
- בדיקה כללית או טיפול שלא דורש חלפים
- בחירה: "אחר" - מלאי לא משתנה

**7.4 מניעה: אם אין חלף דרוש:**
- ❌ **לא יכול לפתוח כרטיס עבודה** - הכפתור "פתח כרטיס" יהיה מנוטרל עד שיהיה חלף זמין

**7.5 עדכון מלאי אוטומטי (Real-time):**
- ברגע שMechanic בחר חלף:
  - ✓ המלאי מתעדכן מיידי (-1)
  - ✓ לא מחכה לסיום העבודה
  - ✓ כל בחירה = מורידה כמות ב-1

**7.6 דוחות צריכה:**
- דוח יומי: "כמה חלפים נצרכו היום"
- דוח לפי סוג רכב: "Volkswagen צורך יותר בלמים מBMW"
- דוח לפי עובד: "עובד X השתמש בY חלפים"

## 4. Non-Functional Requirements

### **NFR-1: ביצועים**
Kanban Board ומסך סטטוסים חייבים להתעדכן בפחות מ-2 שניות (real-time).

### **NFR-2: זמינות**
המערכת תפעל ב-99% זמינות במהלך שעות פעילות המוסך.

### **NFR-3: עקביות נתונים**
- State Machine בBackend יאכוף transitions חוקיים בלבד
- ללא מעבר סטטוסים לא הגיוני
- כל סיום דורש אישור מפורש

### **NFR-4: שימושיות**
- Kanban עם **כפתורים בלא Drag & Drop**
  - כפתור "קבל" (Pending → In Progress) - אוטומטי
  - כפתור "סיים טיפול" (In Progress → Completed) - עם אישור
- ניהול מלא: Pending → Completed ב-2 לחיצות בלבד
- ממשק מינימליסטי - "מינימום קליקים"
- בחירה מרשימות בלבד (לא הקלדה)

### **NFR-5: אבטחה**
- אימות משתמשים (Username/Password)
- כל התקשורת בHTTPS
- הרשאות לפי role (Manager רואה הכל, Mechanic רואה שלו)

### **NFR-6: קיבולת**
- תמיכה ב-10 עובדים בו-זמנית
- ניהול עד 5,000 לקוחות
- ניהול עד 50,000 כרטיסי עבודה
- ניהול עד 1,000 סוגי חלפים

## 5. Assumptions

**זמינות מכשירים:**
- המשתמשים יחזיקו בעמדת מחשב יציבה במוסך

**מספרי טלפון תקינים:**
- לקוחות יספקו מספר טלפון לWhatsApp

**חיבור אינטרנט יציב:**
- אינטרנט רציף במוסך לסנכרון נתונים

**Compatibility Matrix קיים:**
- בעל המוסך יספק טבלת התאמה: חלף X ↔ רכב Y

**שפה עברית בלבד:**
- קהל היעד: ישראל בלבד

## 6. Constraints

**פיתוח Web בלבד:**
- ללא Native Mobile ב-MVP
- Desktop בלבד (לא responsive)

**מסגרת זמן אקדמית:**
- סמסטר אחד
